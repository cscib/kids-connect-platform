1. Purpose and Scope

This document defines the technical architecture for Maltese Quest V1. It specifies the logical modules, their responsibilities, their APIs, and how they communicate. It also defines the boundary between the Maltese Quest product layer and the Kids Connect Platform layer so that platform services built for V1 can be reused by Kids Connect without a rebuild.

2. Layer Model

The architecture is organised into three layers. Each layer has a clear owner, a clear boundary, and a clear set of responsibilities.

3. Module Map

The system is divided into seven logical modules. Each module maps to one layer. Modules communicate through defined API contracts, not direct database access across boundaries.

4. Module Detail

4.1 Identity and Consent Service

Layer: Kids Connect Platform

Responsibilities

  • Parent sign-up, email verification, and login.
  • Social sign-in via Google and Apple.
  • Consent record creation and storage with timestamp and checkbox states.
  • Child profile activation gated on consent completion.
  • Session token issuance using a token-based identity system.
  • Token federation interface for future Kids Connect reuse.

Key data owned

  • Parent account record.
  • Consent record: parent ID, timestamp, four checkbox states, IP address.
  • Session tokens and refresh tokens.

APIs exposed

  • POST /auth/signup — Create parent account and trigger verification email.
  • POST /auth/verify-email — Confirm email token and activate parent account.
  • POST /auth/login — Authenticate parent and return session token.
  • POST /auth/social — Social login via Google or Apple.
  • POST /consent/record — Store consent record on completion of consent flow.
  • GET /consent/status — Return consent status for a parent account.
  • POST /auth/child-token — Issue a child session token after PIN or parent approval.
  • POST /auth/refresh — Refresh an expiring session token.

API Contract Reference

Platform hook

The token-based identity system must support federation from day one. When Kids Connect launches, child and parent tokens issued here must be valid across both Maltese Quest and Kids Connect without re-authentication.

4.2 Parent and Child Profile Service

Layer: Kids Connect Platform

Responsibilities

  • Household creation and management.
  • Child profile creation under a parent account.
  • Age band assignment based on child age field.
  • PIN creation, storage, and verification.
  • Parent approval login path for households without a PIN.
  • Optional second parent or guardian role on a household.
  • First-time experience flag per child profile.
  • Timezone storage for streak and notification timing.

Key data owned

  • Household record: name, timezone, parent IDs.
  • Child profile record: first name, age, age band, avatar ID, PIN hash, first-time flag.
  • Parent-child relationship record.

APIs exposed

  • POST /households — Create a new household.
  • GET /households/:id — Return household detail.
  • POST /households/:id/children — Create a child profile under a household.
  • GET /children/:id — Return child profile detail.
  • PATCH /children/:id — Update child profile fields including age band.
  • POST /children/:id/pin — Set or update child PIN.
  • POST /children/:id/pin/verify — Verify child PIN and return child session token.
  • POST /children/:id/parent-approval — Trigger parent approval login notification.
  • GET /children/:id/first-time — Return first-time experience flag status.
  • DELETE /children/:id/first-time — Clear first-time flag on quest map unlock.

API Contract Reference

The endpoint list in this section is architectural in scope only. Detailed request/response schemas, authentication rules, validation rules, error codes, pagination, idempotency, and endpoint-specific behaviors are defined in api-contract-specifications.md.

Platform hook

The household model, child profile structure, and parent-child relationship record must be reusable by Kids Connect without schema changes. Kids Connect will add messaging permissions and contact visibility on top of the same profile records.

4.3 Contact and Permissions Service

Layer: Kids Connect Platform

Responsibilities

  • Contact request creation, approval, and rejection.
  • Two-parent approval model: requesting parent approves outbound, receiving parent approves inbound.
  • Approved contacts graph storage and retrieval.
  • Permission level assignment: challenge only, learning companion, future chat enabled.
  • Permission level upgrade and downgrade with audit trail.
  • Contact revocation and block, both immediate and permanent.
  • Contact request expiry after 7 days for outbound approval and 30 days for inbound approval.

Key data owned

  • Contact request record: requester child ID, requester parent ID, target details, status, timestamps.
  • Approved contact record: child A ID, child B ID, permission level, approval timestamps, change history.
  • Block record: blocking child ID, blocked child ID, reason code, timestamp.

APIs exposed

  • POST /contacts/requests — Create a contact request.
  • GET /contacts/requests/:id — Return contact request detail.
  • POST /contacts/requests/:id/approve — Approve a contact request and set permission level.
  • POST /contacts/requests/:id/reject — Reject a contact request.
  • GET /contacts/:childId — Return approved contact list for a child.
  • PATCH /contacts/:contactId/permission — Change permission level for an approved contact.
  • DELETE /contacts/:contactId — Revoke an approved contact immediately.
  • POST /contacts/:contactId/block — Block a contact permanently.

API Contract Reference

The endpoint list in this section is architectural in scope only. Detailed request/response schemas, authentication rules, validation rules, error codes, pagination, idempotency, and endpoint-specific behaviors are defined in api-contract-specifications.md.

Platform hook

The approved contacts graph is the core social graph for Kids Connect. The CHAT_ENABLED permission level is a placeholder in V1 but the field must exist in the schema from day one so Kids Connect can activate it without a migration.

4.4 Safety and Alerting Service

Layer: Kids Connect Platform

Responsibilities

  • Event logging for all child interaction events.
  • Alert classification into informational, warning, and action required severity levels.
  • Parent notification triggering on alert generation.
  • Alert resolution tracking with parent action recorded.
  • Account pause and reactivation.
  • Activity log retention for legal and audit purposes.
  • Unusual activity detection rules engine, rules to be defined before build.

Key data owned

  • Interaction event log: child ID, event type, timestamp, related contact ID if applicable, device ID.
  • Alert record: child ID, severity, description, status, parent action taken, timestamps.
  • Account pause record: child ID, paused by parent ID, timestamp, reactivation timestamp.

APIs exposed

  • POST /events/log — Log a child interaction event. Called by MQ and KCP services.
  • GET /alerts/:parentId — Return all alerts for a parent account.
  • GET /alerts/:alertId — Return alert detail and related activity log.
  • POST /alerts/:alertId/resolve — Resolve an alert with action taken recorded.
  • POST /children/:id/pause — Pause a child account immediately.
  • POST /children/:id/resume — Reactivate a paused child account.
  • GET /activity-log/:childId — Return activity log for a child. Premium feature for full history.

API Contract Reference

The endpoint list in this section is architectural in scope only. Detailed request/response schemas, authentication rules, validation rules, error codes, pagination, idempotency, and endpoint-specific behaviors are defined in api-contract-specifications.md.

Critical requirements

Every event log write, alert generation, and revocation execution must be confirmed. If a write fails the system must retry and alert the engineering team. A missed safety event is a legal and ethical failure, not just a technical one.

4.5 Learning Content and Progression Service

Layer: Maltese Quest

Responsibilities

  • Quest map structure: sections, nodes, milestones, and lock state per child.
  • Lesson delivery: activity sequences, content retrieval, and activity type routing.
  • Curriculum alignment to A1 to A2 level Maltese content bands.
  • Progress tracking: lesson completion, accuracy, retry counts, session length.
  • Streak calculation: absence detection, streak maintenance, streak reset, comeback bonus.
  • XP calculation: activity type, accuracy, streak status, and age band inputs.
  • Badge threshold evaluation and badge award.
  • Narrative unlock triggering on milestone completion.
  • Review loop generation for weak vocabulary or phrases.
  • First-time tutorial sequence delivery.

Key data owned

  • Quest map state per child: node completion status, lock state, milestone status.
  • Lesson record: unit, theme, activity sequence, content IDs.
  • Activity record: type, content reference, correct answer, prompt ID.
  • Child progress record: XP total, streak count, badge list, lesson completion history.
  • Streak record: last active date, current streak, longest streak, absence threshold.

APIs exposed

  • GET /quest-map/:childId — Return quest map with node states for a child.
  • GET /lessons/:lessonId — Return lesson detail and activity sequence.
  • POST /progress/lesson-complete — Record lesson completion and trigger XP and badge evaluation.
  • POST /progress/activity-complete — Record individual activity completion with accuracy data.
  • GET /progress/:childId — Return full progress summary for a child.
  • GET /streak/:childId — Return current streak status and history.
  • POST /streak/check-absence — Evaluate absence and return streak status.
  • GET /badges/:childId — Return earned and in-progress badges for a child.
  • GET /review/:childId — Return review activity list for weak content areas.

4.6 Challenge and Recording Service

Layer: Maltese Quest

Responsibilities

  • Preset prompt library management and retrieval.
  • Voice recording capture, storage, and retrieval within challenge context only.
  • Challenge object creation: sender ID, recipient ID, prompt ID, recording reference, timestamp.
  • Challenge delivery to recipient challenge inbox.
  • Challenge response capture and attachment to original challenge object.
  • Preset reaction sending on challenge response.
  • Fallback activity routing when microphone permission is denied.
  • Recording storage policy enforcement: temporary or permanent, to be confirmed in open questions.
  • Microphone permission status tracking per device per child profile.

Key data owned

  • Preset prompt record: ID, Maltese phrase, English translation, audio file reference, unit alignment.
  • Challenge record: sender child ID, recipient child ID, prompt ID, recording reference, status, timestamps.
  • Recording record: child ID, challenge ID, audio file reference, duration, storage expiry if applicable.
  • Microphone permission record: child ID, device ID, status, timestamp.

APIs exposed

  • GET /prompts — Return available preset prompts for a lesson unit.
  • POST /recordings/upload — Upload a voice recording and return a recording reference.
  • POST /challenges — Create and send a challenge object.
  • GET /challenges/inbox/:childId — Return challenge inbox for a child.
  • GET /challenges/:challengeId — Return challenge detail including prompt and recording reference.
  • POST /challenges/:challengeId/respond — Attach a response recording to a challenge.
  • POST /challenges/:challengeId/react — Send a preset reaction to a completed challenge.
  • GET /recordings/:recordingId — Stream a recording with permission checks against challenge context.
  • POST /mic-permission — Log microphone permission status for a device and child profile.
  • GET /mic-permission/:childId — Return microphone permission status for a child on this device.

API Contract Reference

The endpoint list in this section is architectural in scope only. Detailed request/response schemas, authentication rules, validation rules, error codes, pagination, idempotency, and endpoint-specific behaviors are defined in api-contract-specifications.md.

Recording access rules

A recording may only be retrieved in the context of its challenge object. No recording should be accessible by URL alone. All recording retrieval must be permission-checked against the challenge ID and the requesting child or parent account. Parent recording review is a premium feature and must be gated at the API level, not just the UI level.

4.7 Analytics and Event Logging Service

Layer: Shared Infrastructure

Responsibilities

  • Shared event bus receiving events from both MQ and KCP services.
  • Session event logging: app open, session duration, screens visited.
  • Learning event logging: lesson start, lesson complete, activity type, XP earned, badge awarded.
  • Social event logging: challenge sent, challenge received, challenge responded, reaction sent.
  • Safety event forwarding to Safety and Alerting Service.
  • Progress data aggregation for parent progress review screens.
  • Streak and XP summary data for parent dashboard headline metrics.
  • Data retention policy enforcement per event type.

Key data owned

  • Raw event log: event type, child ID, timestamp, metadata, source service.
  • Aggregated progress summary: pre-computed per child for fast dashboard loading.

APIs exposed

  • POST /events — Ingest an event from any service, validate schema, and route to the correct store.
  • GET /analytics/progress/:childId — Return aggregated progress data for parent progress review.
  • GET /analytics/dashboard/:childId — Return headline metrics for parent dashboard card.
  • GET /analytics/speaking/:childId — Return speaking challenge history for progress review.
  • GET /analytics/streak/:childId — Return streak history and heatmap data.
  • GET /analytics/badges/:childId — Return badge history with dates and trigger events.

5. Communication Patterns

5.1 Synchronous API calls

All user-facing interactions use synchronous REST API calls. The calling service waits for a response before continuing. Examples: lesson retrieval, challenge creation, PIN verification.

5.2 Asynchronous events

Background processes use asynchronous events via the shared event bus. The calling service fires and forgets. The analytics and safety services consume events independently. Examples: XP calculation on lesson complete, alert classification on unusual activity detection, notification sending on contact approval.

7. Security Requirements

7.1 Authentication

  • All API endpoints except sign-up and login require a valid session token.
  • Child session tokens are scoped to the child profile and cannot access parent account data.
  • Parent session tokens can access their own household and child profiles only.
  • Tokens must expire and refresh. Refresh token rotation on every use.

    • 7.2 Data access rules

  • A child can only access their own quest map, progress, and challenge inbox.
  • A child can only send challenges to contacts in their approved contacts list.
  • A parent can only access profiles within their own household.
  • Recording retrieval is challenge-scoped. No recording is accessible outside its challenge context.
  • Premium features must be gated at the API level, not just the UI level.

    • 7.3 Child data protection

  • No child surname, address, photo, or school name stored in V1.
  • Voice recordings stored with expiry policy, to be confirmed in open questions.
  • Consent record must be stored before any child data is collected.
  • Parent can request deletion of all child data at any time.
  • GDPR and applicable child data protection laws apply from day one, not from scale.
